= Quarkus Jimmer Extension

include::./includes/attributes.adoc[]

Use Jimmer's data access APIs with Quarkus CDI, datasources, and transaction management.

== Installation

This source branch currently uses coordinates `io.github.flynndi:quarkus-jimmer:0.0.1.CR60` and Jimmer `0.12.3`.
Build and install the branch artifacts locally; the already published CR60 artifact does not include this upgrade.
Use the same Jimmer version for the entity APT/KSP processor and runtime; older published extension versions retain their own dependency versions.

For instance, with Maven, add the following dependency to your POM file:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.github.flynndi</groupId>
    <artifactId>quarkus-jimmer</artifactId>
    <version>0.0.1.CR60</version>
</dependency>
----

For Java entities, configure `org.babyfish.jimmer:jimmer-apt:0.12.3` as the annotation processor.
For Kotlin entities, configure `org.babyfish.jimmer:jimmer-ksp:0.12.3` with your Kotlin/KSP build setup.

[[optional-integrations]]
== Optional integrations

Core data access uses CDI, Agroal, Narayana, and Jackson.
Scheduler, Quartz, Redis, Caffeine, the HTTP server, and REST Client integrations are optional.
Add `io.quarkus:quarkus-scheduler` for periodic transaction-cache retry, or `io.quarkus:quarkus-quartz`
when the application needs Quartz. Quarkus selects the scheduler implementation without registering a second copy of the job.

[cols="1,2,2",options="header"]
|===
|Integration |Application dependency |Activation
|Transaction-cache periodic retry |`io.quarkus:quarkus-scheduler` or `io.quarkus:quarkus-quartz` |A managed datasource uses transaction triggers; interval defaults to `5s`, and `off` disables retry
|Redis / Caffeine cache adapters |`io.quarkus:quarkus-redis-client` / `io.quarkus:quarkus-caffeine` as used by the application |Explicit application cache factory or binders; installing a dependency does not enable caching
|REST exception translation |`io.quarkus:quarkus-rest-jackson` |Set `quarkus.jimmer.error-translator.disabled=false`
|OpenAPI and TypeScript endpoints |HTTP support and JAX-RS/Quarkus REST metadata APIs, normally supplied by `io.quarkus:quarkus-rest` |Explicitly configure the endpoint paths
|Swagger UI |`io.quarkus:quarkus-swagger-ui` |Configure `quarkus.swagger-ui.urls` to reference a document; production also requires `always-include=true`
|Default outbound microservice HTTP exchange |`io.quarkus:quarkus-rest-client` |Configure `quarkus.jimmer.micro-service-name`; auto-enabled when the dependency is present, and replaceable by an application exchange
|Inbound microservice HTTP exporter |`io.quarkus:quarkus-vertx-http` or an extension providing it |Configure `quarkus.jimmer.micro-service-name`; auto-enabled when HTTP is present
|===

Required extensions are checked when an integration is explicitly enabled. Disabled integrations do not register
their routes or beans. Deployment SPI libraries used to contribute routes and exception mappers do not themselves
install a server. The REST Client Jackson provider is unnecessary for the bridge's string transport;
the bridge uses the application's Jackson mapper for payload conversion.

Microservice transports use the existing `quarkus.jimmer.micro-service-name` setting and available Quarkus
capabilities, without additional transport switches. Outbound exchange does not require an HTTP server,
and the exporter does not require REST Client. An application-provided `MicroServiceExchange` replaces the
default exchange and can operate without either HTTP integration. A managed microservice client still needs
one resolvable exchange; missing or ambiguous exchanges are reported during the build.

The default microservice bridge reuses one REST client per target service. The exchange owns these clients
and closes them when its CDI bean is destroyed, including dev-mode reload. Shutdown waits for calls already
in progress before closing their clients; subsequent calls are rejected. ID collections and exporter responses
are serialized as JSON through the application's mapper, including string/UUID IDs and associated-entity tuples.
Custom mappers must retain Jimmer's Jackson support for immutable entity values.

REST exception translation is now disabled by default. Enable it explicitly with
`quarkus.jimmer.error-translator.disabled=false`; setting only its status code or debug options does not enable it.
It requires REST Jackson and returns `application/json`. Core Jackson support alone does not install a REST JSON writer.

Applications upgrading from the previous defaults must declare the extensions they use. Jimmer document
endpoints require an explicit path:

[source,properties]
----
quarkus.jimmer.client.openapi.path=/openapi.yml
----

TypeScript uses `quarkus.jimmer.client.ts.path`.
Relative paths use Quarkus's non-application root, while absolute paths retain their explicit location.

Document generation has three separate responsibilities: `Metadatas` adapts JAX-RS/Quarkus REST API declarations,
`OpenApiDocumentGenerator` and `TypeScriptGenerator` render resolved Jimmer metadata, and the Vert.x handlers
read the request's `groups` parameter and serve the resulting YAML or ZIP. The generators can also be called
with resolved metadata and configuration without a routing context or CDI lookup. Generation remains on demand;
group filtering, configuration names, and output formats are unchanged.

The HTTP extension hosts the document routes; the metadata adapter additionally requires JAX-RS and Quarkus REST
API types on the runtime classpath. These are supplied by `quarkus-rest` or `quarkus-rest-client`; a REST server
implementation is not itself required for generation. Missing metadata APIs are reported during the build when
a document endpoint is configured. The `jimmer-client` generation dependency remains included in this release.

[[swagger-ui]]
== Swagger UI

Add `io.quarkus:quarkus-swagger-ui` to applications that need a UI. This standalone extension supplies the HTML,
JavaScript, CSS, icons, and resource serving. Jimmer retains its own OpenAPI generator and group filtering;
the SmallRye OpenAPI scanner is not required. The Jimmer extension no longer depends on `jimmer-client-swagger`
or supplies a UI template, CDN fallback, or static resource handlers. Its Dev UI card links to the native
Swagger UI when the application includes and enables it.

Jimmer-specific schemas remain available: `@FetchBy` describes the declared fetcher's selected fields and
nested associations, DTO and generic types retain their generated schemas, and declared business exceptions
retain their `family`/`code` fields and alternative response schemas. These are standard OpenAPI document
features produced by `jimmer-client`, so the native UI can display them without a Jimmer JavaScript plugin.
The UI does not discover arbitrary fetchers chosen at runtime; the API's metadata must describe its return shape.

[source,xml]
----
<dependency>
    <groupId>io.quarkus</groupId>
    <artifactId>quarkus-swagger-ui</artifactId>
</dependency>
----

[source,properties]
----
quarkus.jimmer.client.openapi.path=/jimmer/openapi.yml
quarkus.swagger-ui.path=/jimmer/swagger
quarkus.swagger-ui.urls.jimmer=/jimmer/openapi.yml
# Add this only when production should include the UI:
# quarkus.swagger-ui.always-include=true
----

Quarkus includes the UI in dev and test modes by default. Production requires the build-time
`quarkus.swagger-ui.always-include=true` setting; `quarkus.swagger-ui.enabled=false` can disable an included UI
at runtime. Visit `/jimmer/swagger/`: the native UI uses a directory of resources rather than Jimmer's former
single HTML endpoint. The former no-metadata/no-API HTML pages are also removed; inspect the specification
endpoint and its response when diagnosing a missing or empty document.

[cols="1,2",options="header"]
|===
|Removed setting or behavior |Replacement
|`quarkus.jimmer.client.openapi.ui-path` |`quarkus.swagger-ui.path`
|`quarkus.jimmer.client.openapi.ref-path` |`quarkus.swagger-ui.urls.<name>`, including an external absolute URL
|`/openapi.html?groups=public` |A named document URL containing `?groups=public`
|===

These settings are not aliases: remove the old keys from application configuration. For example, the UI can
offer separate groups while the Jimmer specification endpoint continues to generate each document on request:

[source,properties]
----
quarkus.swagger-ui.urls.public=/jimmer/openapi.yml?groups=public
quarkus.swagger-ui.urls.admin=/jimmer/openapi.yml?groups=admin
quarkus.swagger-ui.urls-primary-name=public
----

The UI does not forward its own `groups` query parameter to the document endpoint. Quarkus uses configured
`urls` values verbatim: specify the document's final browser-visible path or a complete URL, including any
HTTP/non-application/management root prefix. The examples use absolute paths to avoid ambiguity between roots.

Group selection follows Jimmer's metadata rules. In Jimmer 0.12.3, a grouped request only includes services
with declared service-level groups, and the request must contain all groups declared by that service.
Method-only groups do not make an ungrouped service visible. Use separate service groups for the `public`
and `admin` documents above; a service declaring both requires `?groups=public,admin`.

With `quarkus.management.enabled=true`, Jimmer document routes run on the management server. The native UI
also uses that server by default, controlled by `quarkus.smallrye-openapi.management.enabled` even when using
standalone Swagger UI. If the UI and document are placed on different servers, configure the document's full
URL and the appropriate CORS policy. For "Try it out" against application endpoints from the management port,
configure `quarkus.jimmer.client.openapi.properties.servers[0].url` with the application API address and allow
the UI origin through the application's Quarkus HTTP CORS settings. Standalone Swagger UI does not apply the
SmallRye OpenAPI scanner's automatic server-address or CORS adjustments.

== Dev UI

In dev mode, open Quarkus Dev UI (normally `/q/dev-ui/`) and select the Jimmer card.
No additional Jimmer UI dependency is required. The card provides:

* *Overview*: build-time language and feature configuration, datasource names and database kinds,
  plus the entity, ID type, and datasource binding of discovered repositories.
* *Model*: searchable entities and their declared properties, including IDs, nullable types,
  associations and target entities, inherited properties, transient properties, and logical deletion.
* *Runtime*: client activation and initialization state, selected configuration, and the actual dialect,
  connection manager, transaction settings, cache operator and cache counts of an initialized client.
* *Schema yaml* and *TypeScript*: links to configured document endpoints.
* *Swagger UI*: a link to the application's optional `quarkus-swagger-ui`, using its native path and
  management-server configuration. The standalone Swagger extension does not supply its own Dev UI card;
  the Jimmer card supplies this navigation without requiring the SmallRye OpenAPI scanner.

Overview and Model use build-time Jandex metadata. Viewing them does not create a SQL client, query a database,
or read database contents. Datasource URLs and credentials are not included. The model describes source
declarations, not live database schema or the final mapping after runtime customizers and naming strategies.
Only explicitly declared table names are displayed.

Integration status distinguishes dependency availability and adapter registration. Redis and Caffeine entries
describe availability only, not whether the application has configured or used a cache. The Runtime page combines
the registered retry task with its interval and global scheduler configuration; this is configuration status,
not a scheduler health check or a guarantee that the task has executed.

Repository entries cover generated legacy repositories and discovered subclasses of
`AbstractJavaRepository` / `AbstractKotlinRepository`. An application-owned repository's datasource is
reported only when its SQL-client injection point has a recognizable binding. Manual construction,
custom qualifiers, or ambiguous injection points are shown as unknown, with an explanation.
Arbitrary implementations of the repository interfaces are not inferred.

Runtime uses Quarkus's native JSON-RPC integration, available only in local development mode.
Opening the page fetches client states; choose *Inspect* to load a client's details, or *Refresh clients*
to update the snapshot. There is no background polling. Both actions inspect ArC's existing contextual
instances without creating a client, obtaining a database connection, or running initialization callbacks.
An uninitialized client therefore has configuration but no actual settings until normal application use
initializes it. Inactive, missing, ambiguous, or unsupported client scopes are reported explicitly.

Configured values and actual client settings are separate: customizers may override configuration.
Actual inspection supports Jimmer's native Java and Kotlin client implementations in shared CDI scopes.
Custom client implementations remain opaque, and unsupported custom cache registries have unknown cache
counts. Cache counts describe enabled registrations, not cached records, cache contents, or hit rates.
The page never loads, evicts, or flushes caches. Connection URLs, credentials, and raw exception messages
are not exported. The cache retry interval is a configured value, not a scheduler health check; the
transaction completion contract is described in <<transaction-cache>>.

The Runtime page and its JSON-RPC provider are not registered in test or production mode. Interactive SQL,
client initialization controls, and transaction/cache mutation actions are outside this Dev UI's scope.

== Configuration validation

SmallRye Config handles value conversion, enums, and missing required values. Jimmer-specific checks use
Quarkus `ConfigurationException`, including complete property keys for the default or named datasource.
They do not install a global config validator or require Hibernate Validator.

Build-time checks cover language selection, negative TypeScript indentation, invalid HTTP error settings,
and invalid document route paths. Runtime initialization checks active datasource settings, including
positive batch sizes, a nonnegative offset optimization threshold, command join counts from 0 through 8,
a default reference fetch type other than `AUTO`, and the configured dialect's class and public constructor.
Multiple configuration problems are reported together. Dialect validation does not invoke its constructor
or static initializer. Manual client factories reuse the datasource checks.

Inactive datasources skip these runtime semantic checks. ConfigMapping conversion still applies to all mapped
values: an invalid integer or enum cannot be hidden by deactivating its datasource. Validation does not create
SQL clients, instantiate SPI beans, or probe database connections. Client and database failures remain subject
to the existing lazy initialization lifecycle.

SQL logging flags retain their current semantics: `show-sql` selects the logging executor; `pretty-sql` and
`inline-sql-variables` configure the default formatter. A supplied formatter takes precedence. These flags do
not impose Spring's logging restrictions on custom executors or formatters. The modern database-validation key
continues to take precedence over its deprecated alias.

== Application repositories

Write repositories as ordinary CDI classes. The extension supplies the SQL client; the application supplies the repository implementation.
The optional base classes provide common operations and are public inheritance contracts.
Use `@Singleton` for constructor-injected subclasses; these base classes have no no-argument constructor
for a normal-scope client proxy. CDI injection and transaction interceptors remain available.

[source,java]
----
import jakarta.inject.Singleton;
import jakarta.inject.Inject;
import org.babyfish.jimmer.sql.JSqlClient;
import io.quarkiverse.jimmer.runtime.repo.support.AbstractJavaRepository;

@Singleton
public class BookRepository extends AbstractJavaRepository<Book, Long> {
    @Inject
    public BookRepository(JSqlClient sql) {
        super(sql);
    }
}
----

The Kotlin equivalent uses `quarkus.jimmer.language=kotlin`:

[source,kotlin]
----
import jakarta.inject.Singleton
import jakarta.inject.Inject
import org.babyfish.jimmer.sql.kt.KSqlClient
import io.quarkiverse.jimmer.runtime.repo.support.AbstractKotlinRepository

@Singleton
class BookRepository @Inject constructor(sql: KSqlClient) :
    AbstractKotlinRepository<Book, Long>(sql)
----

`findById` returns a nullable entity, and `save` returns a Jimmer save result.
Inject these repositories into services through CDI, and use `@Transactional` where the application needs a transaction boundary.
The new `JavaRepository` and `KotlinRepository` interfaces do not trigger implementation generation or derived queries.
Implement custom queries with Jimmer DSL in the concrete class.

Direct injection of `JSqlClient` or `KSqlClient` is also a supported application entry point; repositories are optional.
For a named datasource, put `@DataSource("name")` on the injected client or the repository constructor's client parameter.
See xref:repository-migration.adoc[Repository contracts and migration] for the public API boundary and migration from the compatibility APIs.

== Data sources and CDI

Prefer injecting `JSqlClient` or `KSqlClient`.
CDI-managed clients are application-scoped: ArC creates the underlying client lazily when its proxy is first used.
Each datasource has one managed client, and the compatibility client containers expose that same CDI proxy.
Injecting a proxy alone does not initialize the client or validate its active state; invoking an inactive client fails on first use.
Construction failures are reported as CDI creation errors with the underlying cause preserved.

Named Jimmer clients use the corresponding Quarkus `@DataSource("name")` qualifier and do not require a default datasource.
`quarkus.jimmer."name".active=false` disables the Jimmer client for that datasource without disabling the datasource itself.
By default, Jimmer follows the datasource's active state; an inactive datasource cannot supply an active Jimmer client.
Use programmatic CDI lookup when choosing between active and inactive clients, and check the bean's active state before obtaining it.

Jimmer SPI beans such as filters, customizers, initializers, scalar providers, and draft interceptors are retained automatically.
They do not need `@Unremovable` merely because Jimmer discovers them dynamically.
SPI beans may inject the matching client for later use, but must not call back through its proxy during construction,
`@PostConstruct`, `customize`, or `initialize` while that client is being created.
An `Initializer` should use the client passed to its callback.
Only the selected language's filters, customizers, and initializers are instantiated.
Connection and dialect defaults are completed after user customizers run.
An explicit dialect skips JDBC probing; replacing the connection manager makes detection use that connection manager.

`SqlClients.java(...)` and `SqlClients.kotlin(...)` build independent clients immediately and report construction failures at the factory call.
The automatic `TransactionCacheOperator` belongs only to the CDI-managed client.
For a manual client that needs transaction-aware cache invalidation, configure a dedicated operator through its builder.

`quarkus.jimmer.database-validation-mode` takes precedence over the deprecated `quarkus.jimmer.database-validation.mode` key.

The GraphQL integration and its APT/KSP modules have been removed from this development version.

[[transactions]]
== Transactions

`TxConnectionManager.executeTransaction(propagation, callback)` uses the same Narayana interceptors as Quarkus `@Transactional` methods.
The JDBC connection is acquired inside that transaction boundary and closed before the callback's transaction boundary ends.
Agroal handles enlistment in the current JTA transaction.

[cols="1,2,2",options="header"]
|===
|Propagation |Without an existing transaction |With an existing transaction
|`REQUIRED` |Start and complete a transaction |Participate in the caller's transaction
|`REQUIRES_NEW` |Start and complete a transaction |Suspend the caller's transaction, complete a new transaction, then resume the caller
|`SUPPORTS` |Run without a transaction |Participate in the caller's transaction
|`NOT_SUPPORTED` |Run without a transaction |Suspend the caller's transaction, run without a transaction, then resume the caller
|`MANDATORY` |Reject before invoking the callback |Participate in the caller's transaction
|`NEVER` |Run without a transaction |Reject before invoking the callback
|===

`MANDATORY` without a transaction throws `TransactionalException` with a `TransactionRequiredException` cause.
`NEVER` with a transaction throws `TransactionalException` with an `InvalidTransactionException` cause.
A transaction marked rollback-only still counts as an existing transaction.

By default, a `RuntimeException` or `Error` rolls back a newly created transaction or marks a participating transaction rollback-only.
Catching the exception in the caller does not clear that mark.
Quarkus `@Rollback` annotations on exception types retain their normal Narayana semantics.
Unlike the previous programmatic runner, checked exceptions do not trigger rollback by default.
This also applies to checked exceptions thrown from Kotlin callbacks: use `@Rollback(true)` on the exception type when rollback is required.
ArC wraps an undeclared checked exception in `ArcUndeclaredThrowableException`, preserving it as the cause;
that wrapper does not change the rollback decision already made for the original exception.
Failures in a `REQUIRES_NEW` or `NOT_SUPPORTED` callback restore the suspended caller's transaction without marking it rollback-only;
an exception escaping an enclosing transactional method can still trigger that method's rollback rules.

This API is synchronous: a returned `CompletionStage` or publisher is a return value, not asynchronous database work managed by this transaction.
It does not delay transaction completion after the callback returns.
The ordinary `ConnectionManager.execute(...)` methods keep their connection-only behavior and do not start a transaction.

[[transaction-cache]]
== Transaction cache completion

The transaction cache operator writes delayed cache deletion records through the client's connection manager.
With an Agroal datasource participating in JTA, these records commit or roll back with the business changes.
The first Jimmer database event observed in an active transaction registers one completion callback.
The factory publishes events with the client's `@DataSource` qualifier, and the callback collects their datasource names.
The existing `@Default` event qualifier is retained. Observers without a qualifier or with `@Default` continue
to receive events from all clients; observers may select a specific datasource.
Its registration marker belongs to the JTA transaction through `TransactionSynchronizationRegistry`, so
suspension, `REQUIRES_NEW`, and completion on another thread do not share or lose the marker.

Only `STATUS_COMMITTED` triggers a completion flush. Rollback, rollback-only transactions, and transactions
without database events do not trigger one. The callback is a regular JTA synchronization: Narayana runs it
after the interposed synchronization that releases Agroal's connection. Completion flushes only visit operators
for the datasources involved in that transaction, avoiding attempts to borrow a connection held by a suspended
outer transaction on another datasource. Scheduled retries visit all active operators. Each operator runs in its
own `REQUIRES_NEW` transaction, so operators for different datasources are not enlisted together in one flush transaction.

This is eventual cache invalidation. A failure after commit cannot undo the business transaction.
A cache deletion exception rolls back that operator's flush transaction, preserving the delayed deletion
records for a later flush. Other active operators are still attempted. Completion failures are
logged; scheduled retry failures are reported to the scheduler. Deletion can be repeated after a partial
cache operation or a failed flush commit, so cache implementations must support idempotent deletion.
Jimmer's own batching and internal SQL error handling still apply; the extension does not turn failures
that Jimmer handles internally into exceptions or guarantee an immediate empty queue after every commit.

Application-published events without a `@DataSource` qualifier cannot identify an operator and need a later flush.
Events outside an active JTA transaction do not flush immediately: Jimmer's cache listeners may write the
delayed deletion records after the CDI event observer returns. An optional scheduled job processes those records,
using `quarkus.jimmer.transaction-cache-operator-fixed-delay` as its interval.
Add `quarkus-scheduler` or `quarkus-quartz` to register the job. Without either extension, successful commit
callbacks still run and no periodic job is registered. The default interval is `5s`; `off` or `disabled`
disables only this job. `quarkus.scheduler.enabled=false` disables the application's scheduler as a whole.
Without periodic retry, failures, nontransactional events, and records left by an application crash need
an application-arranged retry or a later flush; they are not guaranteed to recover automatically.
The lightweight scheduler checks triggers once per second; applications relying on Quartz-specific
scheduling precision or clustering must add Quartz explicitly.

== HTTP handler lifecycle

The OpenAPI document and TypeScript handlers receive their build-time configuration from recorders.
They do not look up CDI beans or create a request context. Swagger UI and its static assets are managed
by the application's optional Quarkus Swagger UI extension.

Microservice export handlers are CDI singletons. `@ActivateRequestContext` covers dependency resolution,
database access, and response generation; an existing request context is retained, and a context created by
the interceptor is terminated when the synchronous handler returns or throws. The handlers use the default
`JSqlClient` and `ObjectMapper` with standard CDI selection. Missing or ambiguous dependencies fail resolution
instead of selecting an arbitrary bean. ArC caches the selected CDI references, preserving normal-scope
proxies and managing the lifetime of dependent instances.

== REST client metadata

Jimmer's generated clients recognize JAX-RS `@QueryParam`, `@PathParam`, and `@HeaderParam`,
and Quarkus REST's `@RestQuery`, `@RestPath`, and `@RestHeader`.
An unnamed Quarkus query or path parameter uses the parameter name recorded by Jimmer.
Path parameters must declare `@PathParam` or `@RestPath`; implicit matching against URI templates is not inferred.
An unnamed `@RestHeader` follows Quarkus REST's header naming convention
(for example, `contentType` becomes `Content-Type`) and requires compilation with `-parameters`.
`@DefaultValue` supplies the actual default; the binding name is not a default value.

Path parameters are required. Query, header, and multipart parameters may be omitted unless
a runtime-visible non-null annotation or Bean Validation constraint declares otherwise.
A default value permits omission. Bean Validation annotations describe the client contract;
server-side validation still requires the application's validation integration.
Unannotated entity parameters are JSON request bodies, including when `@Consumes` is absent.
Method-level `@Consumes` takes precedence over the resource class.
Bodies retain Jimmer's non-null metadata by default; use a runtime-visible annotation such as
`org.jspecify.annotations.Nullable` for optional bodies. Jimmer 0.12.3 cannot reconcile a nullable
body known only through a class-retained annotation with this runtime parser and will reject it.

Multipart support covers named `@RestForm`/`@FormParam` parameters on methods consuming
`multipart/form-data`, including `FileUpload` and `FilePart`. Wildcard uploads, aggregated form
beans, URL-encoded forms, cookie/matrix bindings, and non-JSON entity bodies are outside this
client metadata contract. They must not be represented as JSON bodies or query parameters.
Standard framework context types, such as `UriInfo`, and Quarkus REST's `RoutingContext`,
`HttpServerRequest`, and `HttpServerResponse` are omitted from generated client parameters.
